# Cli — cross-language developer bootstrap platform

> **Status: V1 shipped, actively iterating.** An arrow-key interactive CLI
> (with a non-interactive/scriptable path), a hardened local plugin
> protocol, two working templates in two languages (Go and Node.js), and
> `bootstrap doctor`/`--verbose` diagnostics are on `main` today. See
> [`docs/architecture/roadmap.md`](docs/architecture/roadmap.md) for what's
> still deferred, and [`CHANGELOG.md`](CHANGELOG.md) for what's shipped so far.

Cli is an **orchestrator**, not a framework replacement, for bootstrapping new
projects. You run one interactive command, answer a few questions (theme,
project type, language, framework, capabilities), and get a working,
production-shaped project — generated by a plugin, not baked into the core.
Templates today: a Go REST API service (`net/http`) and a Node.js HTTP API
service (`node:http`, zero npm dependencies) — see
[ADR-0009](docs/architecture/adr/0009-second-template-cross-language.md).

## Principles

- **Offline first** — no network calls required to generate a project.
- **Plugin first** — templates and capabilities are plugins; the core never
  hard-codes what it can generate.
- **Clean boundaries** — each subsystem is an independently buildable Go
  module; they talk over small, explicit interfaces (see
  [`docs/architecture/overview.md`](docs/architecture/overview.md)).
- **Cross-platform** — Linux, macOS, Windows.
- **Accessible** — the CLI itself respects `NO_COLOR`, offers a minimal
  screen-reader-friendly theme, and never encodes state in color alone.
- **Production quality** — what V1 generates actually builds and passes its
  own tests, not a stub.

## Repository layout

This is a single repository with dedicated long-lived branches per
subsystem, all merged into `main` via pull request (never a direct push to
`main`):

| Branch | Contains |
|---|---|
| `main` | Integration branch; releases are tagged here |
| `architecture` | ADRs, architecture docs, root project scaffolding |
| `cli` | The interactive/non-interactive CLI |
| `core` | Orchestration engine, plugin host, config model, local registry |
| `sdk` | `sdk/go` — the library plugin/template authors use |
| `templates` | Template plugins (`go-rest-api`, `node-rest-api`) |
| `plugins` | Built-in capability plugins (V1: `git-init`, `readme`, `github-actions-ci`) |
| `tests` | Integration/golden tests + CI workflow |

See [`CONTRIBUTING.md`](CONTRIBUTING.md) for the full workflow and
[`docs/architecture/`](docs/architecture/) for ADRs and design docs.

## Quickstart

```sh
make build
./bin/bootstrap new
```

Run this from the repository root: `make build` places the CLI at
`bin/bootstrap` and every template/capability plugin under
`templates/`/`plugins/builtin/` (discovered relative to the current
working directory) — building only `go build -o bootstrap ./cli` skips
the plugins, and `bootstrap new` will fail with "no template plugin
found." See [`docs/cli/usage.md`](docs/cli/usage.md) for `bootstrap
doctor`, a health check for exactly this kind of setup problem.

Answer the prompts (theme → project type → language → framework →
capabilities) and a new project is generated in the current directory. For
scripted/offline use:

```sh
./bin/bootstrap new --answers answers.yaml
```
